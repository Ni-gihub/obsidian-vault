# デザイン設計・検討項目

このノートは、Vampire Survivors攻略サイトのデザインを詳細に決め、最終的に `DESIGN.md` としてまとめるための検討チェックリストである。

現時点では、デザインの数値や見た目を決め切ることが目的ではない。まずはサイトに必要なページ内容・情報構成を考え、その後に視覚デザインやUIの細部を決める。

**未検討の案を決定事項として扱わないこと。** 決まった項目は理由とともに記録し、最終的に `DESIGN.md` へ反映する。

---

## 1. このノートの使い方

### 1.1 検討状況の管理

各項目は、次の状態で管理する。

| 状態 | 意味 |
|---|---|
| 未検討 | まだ具体的な検討を始めていない |
| 検討中 | 候補や参考例を比較している |
| 決定 | 方針・仕様が決まり、理由も説明できる |
| 実装確認済み | 実際の画面で確認し、必要な調整も終わっている |
| 対象外 | 今回は採用しないと判断した |

このファイルのチェック項目は、設計漏れを防ぐための一覧である。チェックを付けること自体を目的にせず、サイトに必要なものだけを決める。

### 1.2 1つの項目を決めるときに残す内容

重要な判断は、可能な範囲で次の情報を残す。

- **決めること：** 何を決定するのか
- **目的：** 何を解決するための判断なのか
- **候補：** 比較した案や参考にした画面
- **決定内容：** 最終的にどうするのか
- **理由：** なぜその案を選ぶのか
- **影響範囲：** どのページ・コンポーネント・画面幅に影響するか
- **状態：** 未検討／検討中／決定／実装確認済み／対象外

### 1.3 関連ドキュメントとの役割分担

| ドキュメント | 管理する内容 |
|---|---|
| [[Vampire Survivors攻略サイト構想]] | サイトを作る目的、対象読者、強み、運用方針 |
| [[サイト構成・コンテンツ分類]] | ページの種類、情報分類、ページ同士の関係 |
| [[攻略記事の品質基準]] | 記事に含めるべき情報と記事ごとの品質 |
| [[アクセス解析・ユーザー行動計測]] | クリック・閲覧の計測目的と候補 |
| **このノート** | デザインとして決めるべき項目、検討順序、未決定事項 |
| `DESIGN.md`（今後作成） | 決定したデザイン原則、トークン、コンポーネントの正式な基準 |

記事の内容そのものや攻略情報の分類を、このノートで二重管理しない。既存ノートを正本として参照する。

## 2. 参考にするデザイン資料

### 2.1 SmartHR Design System

**参考サイト：** [SmartHR Design System](https://smarthr.design/)

デザインの考え方やルールの整理方法を学ぶための主要な参考資料とする。SmartHRの色・形・ブランド表現をそのまま採用するのではなく、デザインを体系化する方法を参考にする。

確認・参考にする観点：

- [ ] デザインシステム全体の情報構成
- [ ] デザイン原則や基本方針の書き方
- [ ] 色を役割ごとに整理する方法
- [ ] タイポグラフィの定義方法
- [ ] 余白・レイアウト・形状の整理方法
- [ ] コンポーネントの説明方法
- [ ] アクセシビリティの扱い
- [ ] ガイドラインを実装や運用に結び付ける方法

**参考にするもの：** 設計の考え方、説明の粒度、情報の整理方法。

**そのまま流用しないもの：** SmartHR固有のブランドカラー、フォント、画面構成、業務アプリ向けの表現。

### 2.2 Idea Boost の DESIGN.md

**参考ファイル：** [engineer-first/idea-boost — DESIGN.md](https://github.com/engineer-first/idea-boost/blob/develop/DESIGN.md)

人とAIエージェントが同じデザイン基準を参照できるように、YAMLの値と本文の意図・使い方を組み合わせている。

確認・参考にする観点：

- [ ] 先頭のYAMLでデザイントークンを定義する方法
- [ ] `colors`、`typography`、`spacing`、`rounded`、`components` の整理方法
- [ ] 数値だけでなく、なぜそのルールにするのかを文章で説明する方法
- [ ] 色や状態を用途・意味で定義する方法
- [ ] コンポーネントの使い方と避けることを明示する方法
- [ ] 決定済みと未実装・未決定を区別する方法

Idea Boostの実装事情に依存する値やルールは持ち込まず、このサイトに必要な項目へ置き換える。

### 2.3 DESIGN.md の形式そのもの

**参考プロジェクト：** [Google Labs DESIGN.md](https://github.com/google-labs-code/design.md)

Idea Boostが採用している形式の背景を確認するための資料。最終的に同じ形式やlintツールを利用するかどうかは、実際に `DESIGN.md` を作る段階で判断する。

### 2.4 参考サイト・参考画面の記録

SmartHR以外にも、記事を読みやすくするWebサイトや、スマートフォンで操作しやすいサイトを調査する。

参考にするときは、サイト全体を漠然と真似るのではなく、次のように記録する。

- 参考URL・画面
- 参考にしたいページ・部品
- どの点が使いやすいと感じたか
- 自分のサイトのどの課題に応用できそうか
- そのまま採用せず変更する点

## 3. デザイン検討の全体順序

現在は**フェーズ1：ページ内容・情報構成**を優先する。色・フォントなどの視覚的な決定は後回しにする。

| フェーズ | 検討内容 | 状態 |
|---|---|---|
| 1 | ページごとの目的・掲載内容・情報の順序 | 検討中 |
| 2 | サイト全体のナビゲーション・ページ間の導線 | 未検討 |
| 3 | デザインコンセプト・デザイン原則 | 未検討 |
| 4 | 色・文字・余白・形状などのデザイントークン | 未検討 |
| 5 | 共通コンポーネントと各ページのレイアウト | 未検討 |
| 6 | PC・タブレット・スマートフォンのレスポンシブ設計 | 未検討 |
| 7 | 操作性・アクセシビリティ・状態表現 | 未検討 |
| 8 | 実装への受け渡し・DESIGN.md作成・画面検証 | 未検討 |

各フェーズは完全に独立しているわけではない。ページ内容を考える中でレイアウト上の問題が見つかったら、必要に応じて前の判断へ戻る。

# フェーズ1：ページ内容・情報構成

## 4. サイト全体で共通して決めること

まず、どのページにも関係する情報の扱いを決める。

### 4.1 ページの目的と入口

- [ ] 各ページに訪問した人が、最初に何を理解できる必要があるか
- [ ] 検索エンジンや外部リンクから直接訪問した場合、サイト内での位置が分かるか
- [ ] ページ単体で目的を果たせるか
- [ ] 次に必要になりそうな情報へ移動できるか
- [ ] トップページを経由しなくても迷わないか
- [ ] 情報を探している人に不要な導入や装飾を強制しないか

### 4.2 ページ内の情報の順序

- [ ] 最初に表示する情報は何か
- [ ] 最も重要な情報をどの位置に置くか
- [ ] 前提知識・条件・手順・結果をどの順序で示すか
- [ ] 補足や詳細情報を本文に置くか、折りたたむか
- [ ] 記事末尾に置く情報は何か
- [ ] 長い記事で目的の箇所へ移動できるか

### 4.3 記事共通の情報

- [ ] パンくずリストを表示するか
- [ ] 記事タイトルの表示方法
- [ ] 本編・DLC・ステージなどの所属情報の見せ方
- [ ] 目次の表示位置・初期状態・開閉方法
- [ ] 記事内リンク・関連記事の配置
- [ ] note記事やYouTube動画への関連リンクの配置
- [ ] 画像・表・動画の説明やキャプションのルール
- [ ] 記事の更新情報をどのように扱うか
- [ ] ゲームバージョン・検証条件などをどの記事に表示するか
- [ ] すべての記事に共通表示する情報と、記事ごとに必要な場合だけ表示する情報の区別

記事冒頭に「この記事で分かること」のような定型要約を置く方針ではない。記事の導入は内容に自然に入れる形を基本とし、同じ説明の繰り返しを避ける。

### 4.4 目次

- [ ] 目次に表示する見出しの階層
- [ ] 目次を常時表示するか、折りたたみ式にするか
- [ ] PCとスマートフォンで表示方法を変えるか
- [ ] スクロール時に目次を固定するか
- [ ] 目次を開閉したときの表示領域
- [ ] 見出しへ移動したときのスクロール位置
- [ ] 現在読んでいる見出しを目次で示すか
- [ ] 長い記事でも目次が使いやすいか

### 4.5 関連情報・ページ間のつながり

- [ ] 関連記事を選ぶ基準
- [ ] 同じステージ・ボス・キャラクター・DLCの関連情報をどう結び付けるか
- [ ] 攻略記事から仕組み解説へ移動する導線
- [ ] 仕組み解説から実践的な攻略記事へ戻る導線
- [ ] noteの先行情報とWebサイトの整理済み記事の相互リンク
- [ ] YouTube動画と関連攻略記事の相互リンク
- [ ] リンク先がない場合の表示
- [ ] リンクが多すぎて本文を読みづらくしない方法

## 5. ページ種類ごとの内容設計

ページの掲載内容や記事ごとの品質基準は、既存の [[サイト構成・コンテンツ分類]] と [[攻略記事の品質基準]] を正本とする。このセクションでは、それらを実際のページ上でどう並べ、どう探せるようにするかを検討する。

### 5.1 ホーム

**決定済み：ホームはサイト内にあるすべてのコンテンツへの案内役・全体案内図とする。主要なコンテンツごとに入口を設け、各カテゴリ・一覧ページから個別記事へ移動できるようにする。個別記事をすべてホームに並べるのではなく、情報のまとまりごとに案内する。**

- [ ] 攻略・金策・アップデート・note・YouTubeの入口の見せ方
- [ ] 攻略の4種類の入口と、それぞれのカテゴリ一覧への案内方法
- [ ] ステージ・ボス・キャラクター・アンロックなど、攻略コンテンツの分類の見せ方
- [ ] 金策の仕組み・基本解説と金策構築の案内方法
- [ ] note・YouTubeページへの案内方法
- [ ] 各コンテンツ入口の表示順
- [ ] ホームから個別記事までの移動経路が分かりやすいか
- [ ] ホームに個別記事への直接リンクも掲載する必要があるか（必要な場合に対象を検討）
- [ ] スマートフォンで全体の案内を見つけやすくする方法

よく参照される記事・新着記事の掲載や、note・YouTubeの最新情報をホームに表示することは、現時点では必須としない。

### 5.2 攻略の一覧・カテゴリページ

**決定済み：攻略トップでは「ステージ攻略」「ボス攻略」「キャラクター情報」「アンロック攻略」の種類別に入口を表示する。本編・DLCを選ぶだけの中継ページは作らない。本編とDLCは、それぞれの種類の一覧ページ内で分類する。各一覧ページには原則として検索・ソート・フィルター機能を設けず、固定した分類と並び順で見つけやすくする。**

- [ ] 攻略トップで4種類の入口をどう見せるか
- [ ] ステージ攻略一覧で、本編とDLCごとのステージをどう分類・表示するか
- [x] **ステージ攻略一覧は画像とステージ名を表示する（具体的なレイアウト形式は未決定）**
- [x] **ステージ攻略一覧は本編を先にし、その後にDLCを新しい順で並べる**
- [x] **一覧に表示する基本情報は画像と名称のみとする**
- [x] **ボス攻略一覧は本編とDLCに分け、基本的に出現ステージの順番で並べる。画像とボス名を表示する**
- [x] **キャラクター情報は本編とDLCに分け、各グループ内はゲーム内と同じ順番にする。画像とキャラクター名を表示する**
- [x] **アンロック攻略は本編とDLCに分け、各グループ内はゲーム内と同じ順番にする。画像とアンロック名を表示する**
- [x] **金策構築は現状の2体の構築を基本とし、新しい構築が増えた場合に同じ一覧へ追加する。複雑な分類は設けない**
- [ ] DLCの並び順・名称・画像などを一覧内でどう扱うか
- [ ] 記事数が少ないカテゴリや、攻略情報がまだないDLCの表示方法
- [ ] 参考サイトを複数調査し、画像＋名称の一覧表示パターンを比較する
- [ ] カード形式を前提にせず、リスト型なども含めて一覧レイアウトを検討する
- [ ] 特にスマートフォン表示は、参考サイトを比較しながら実際の情報量を当てはめて試行錯誤する
- [ ] カテゴリ一覧のカードやリンクに表示する情報
- [ ] 一覧ページから個別記事へ移動する方法
- [ ] スマートフォンで一覧内の分類を探しやすくする方法

### 5.3 ステージ攻略記事

4. 関連するアンロック（記事末尾。該当する場合）

追加で検討すること：

- [ ] クリア条件・生存時間をタイトル付近などに小さく表示する方法
- [ ] ステージ固有ギミックの説明方法
- [ ] 時間ごとの敵の出現情報を表にする条件
- [ ] 敵の画像・名称・出現時間・注意点の見せ方
- [ ] クリアに関係しない敵情報を省く基準
- [ ] 攻略方針と実際のクリア構築のつなぎ方
- [ ] ボス攻略記事が別にある場合のリンク位置
- [ ] 達成条件・達成報酬の表示方法

### 5.4 ボス攻略記事

4. 攻略方針・実際にクリアした構築

追加で検討すること：

- [ ] 出現条件と出現場所をどう見せるか
- [ ] ボスの行動・ギミックを文章、画像、動画のどれで説明するか
- [ ] 複数の攻撃やフェーズがある場合の整理方法

### 5.5 キャラクター攻略ページ

現在の基本方針：

- 本編・DLCごとにページを分ける
- キャラクター一覧はページ上部に常時並べず、折りたたみ式にする
- 一覧から同じページ内の該当キャラクター詳細へ移動できるようにする
- 一般的な基本データの網羅ではなく、性能の活かし方や実践的な攻略知見を中心にする

追加で検討すること：

- [ ] 折りたたみ式一覧の位置・初期状態・開閉方法
- [ ] 一覧内のキャラクター名・アイコン・画像のどれを使うか
- [ ] キャラクター数が多い場合の分類・グループ化（一覧内検索は設けない）
- [ ] DLC内でキャラクターをどう分類するか
- [ ] 一覧から選択したときの移動方法
- [ ] キャラクター詳細の見出し構成
- [ ] 性能・固有能力の説明方法
- [ ] 強み・弱み・活用方法の表現
- [ ] おすすめ構築や相性のよい武器などの見せ方
- [ ] 画像や動画、構築例の配置
- [ ] 目次と折りたたみ式キャラクター一覧の役割分担
- [ ] 詳細が未作成のキャラクターの扱い
- [ ] 一覧の項目数が増えたときのページ内移動の使いやすさ

4. ページ内容がまとまったら、デザインコンセプトと視覚ルールの検討に進む。
5. 最後に決定事項を `DESIGN.md` にまとめる。

### 現時点で決まっている主な方針

- 既存の企業Wikiよりも、実際に攻略へ役立つ情報を詳しく提供する。
- スマートフォンからの閲覧を重視する。
- 読者は検索・note・YouTubeなどから個別ページへ直接訪れることがある。
- 記事には原則として目次を設置する。
- 「この記事で分かること」の定型欄は設けない。
- ボス攻略・ステージ攻略は、攻略方針と実際にクリアした構築を重視する。
- キャラクター情報は本編・DLCごとにまとめ、各グループ内はゲーム内順にする。各キャラクターの掲載内容は画像・入手方法・詳しい性能解説を基本とする。個別ページは作らず、一覧は折りたたみ式にする。
- ボス一覧は本編・DLC別に分け、基本的に出現ステージ順にする。アンロック一覧も本編・DLC別に分け、ゲーム内順にする。
- 金策構築一覧は現状の2体を基本とし、新しい構築が増えた場合に同じ一覧へ追加する。
- 金策は「仕組み・基本解説」と「金策構築」に分ける。
- アップデート情報はバージョンごとにまとめ、無料アップデートとDLCを同じバージョンページで扱う。
- noteは既存のnote記事リンク集を最上部に置き、その下にWebサイト側で付与したタグごとに記事リンクを分けるシンプルな入口ページにする。
- YouTubeは投稿動画を新しい順に並べたシンプルな入口ページにし、動画の視聴はYouTubeへ移動してもらう。攻略に直接関係する動画は、該当する攻略ページに埋め込む。
- サイト内のクリックや閲覧行動を計測し、改善に活かす。

上記はデザイン検討の前提であり、視覚デザインの決定内容ではない。
